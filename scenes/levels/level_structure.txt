Cette procédure explique comment structurer et câbler un niveau (scène de restaurant), à jour avec l'architecture de scènes réutilisables (RestaurantEntities/RestaurantDecor/GameplayCore/HUD).

# -- 1. Vue d'ensemble : ce qui est réutilisable vs propre à chaque niveau -- #

4 scènes réutilisables composent chaque niveau par instanciation :

- RestoX_decor.tscn (une par RESTO, ex: resto_a_decor.tscn) : plancher, murs, éclairage ambiant
- RestaurantEntities.tscn (une par RESTO) : comptoir + PaymentQueueComponent + CounterOrderFlowComponent + CustomerSpawner (vide de tables/nourriture — celles-ci s'ajoutent par niveau via "Editable Children")
- GameplayCore.tscn (UNIVERSELLE, tous restos/niveaux) : LevelManager + OrderFlowComponent + SpawnOrchestratorComponent + DayCycleComponent + WaitingQueueComponent
- HUD.tscn (UNIVERSELLE) : DayClock, Tray_places, EarningsGauge, SpawnButton, TipJarDisplay, LevelIntroScreen, DayResultsScreen, EndOfServicePanel

Propre à CHAQUE niveau (pas réutilisable) :
- Les tables et la nourriture (ajoutées comme "Editable Children" sur l'instance Entities)
- Le NavigationRegion2D (ZoneDeplacement) et son NavigationPolygon
- La position/rotation/scale du WaitingQueueComponent
- Le LevelData (.tres) assigné au LevelManager
- Tous les NodePath de câblage du LevelManager (voir section 8)

# -- 2. Structure d'une scène de niveau (référence : resto_a-level_1.tscn) -- #

RestoX_LevelN (Node2D)
├── RestoXDecor (instance de RestoX_decor.tscn)
├── Entities (instance de RestaurantEntities.tscn, Y Sort Enabled = ON)
│   ├── Comptoir (déjà dans la scène réutilisable)
│   ├── CustomerSpawner (déjà dans la scène réutilisable)
│   ├── player (ajouté par niveau)
│   ├── Table_for_four, Table_pour_deux... (ajoutées par niveau, groupe "nav_obstacles")
│   └── Nourritures (Node2D, Y Sort Enabled = ON, ajouté par niveau)
│       └── (aliments du comptoir)
├── ZoneDeplacement (NavigationRegion2D, propre au niveau — voir section 5)
├── HUD (instance de HUD.tscn)
└── GameplayCore (instance de GameplayCore.tscn)
    ├── LevelManager
    ├── OrderFlowComponent
    ├── SpawnOrchestratorComponent
    ├── DayCycleComponent
    └── WaitingQueueComponent (position/rotation/scale À AJUSTER par niveau)

# -- 3. Étapes pour créer un nouveau niveau -- #

a) Dans l'éditeur, ouvrir une scène de niveau EXISTANTE ET FONCTIONNELLE de ce resto (ex: resto_a-level_1.tscn) — jamais une scène orpheline/ancienne.
b) Scene → Save Scene As... → nouveau nom (ex: resto_x-level_x.tscn), dans le bon dossier scenes/levels/resto_X/
c) Ajuster le décor si besoin (rarement nécessaire, le décor est partagé par resto)
d) Sous Entities : repositionner/ajouter/retirer les tables, la nourriture, le joueur pour ce niveau. Ne pas oublier le groupe "nav_obstacles" sur toute nouvelle table.
e) Refaire le NavigationPolygon de ZoneDeplacement pour matcher la nouvelle disposition (voir section 5-6)
f) Créer/choisir le LevelData (.tres) pour ce niveau (voir section 7)
g) Sur GameplayCore/LevelManager : ASSIGNER le nouveau Level Data — sinon la scène va silencieusement utiliser le level_data par défaut de gameplay_core.tscn (actuellement level_data_restoA-j1.tres) !
h) Revérifier TOUS les NodePath du LevelManager (section 8) — dupliquer une scène dans Godot casse parfois les références si des nœuds ont été renommés/déplacés pendant l'édition.

# -- 4. Pourquoi le Y-Sort doit être groupé -- #

Godot dessine les nœuds selon leur ordre dans l'arbre, pas selon leur position à l'écran. Meubles et personnages doivent vivre sous UN SEUL parent Y-Sort (Entities) pour se trier correctement par profondeur.

# -- 5. NavigationRegion2D par groupe (obstacles) -- #

a) Sélectionner ZoneDeplacement (NavigationRegion2D)
b) Inspecteur → Navigation Polygon → Geometry :
   - Source Geometry Mode → "Group Explicit"
   - Source Geometry Group Name → "nav_obstacles"
c) Chaque table + le Comptoir doivent already avoir (ou recevoir) le groupe "nav_obstacles" (Scene dock → Node → Groups)
d) Rebake (bouton "Bake NavigationPolygon")

Note : "Source Geometry Group Name" ne fait que dire à Godot quel groupe chercher — il ne le crée pas. Le groupe n'existe qu'une fois qu'au moins un nœud y a été ajouté.

# -- 6. agent_radius et limites de la scène -- #

Le agent_radius érode uniformément TOUS les bords du polygone de navigation (contours extérieurs ET obstacles internes). Pour garder une zone marchable jusqu'à un marker de sortie/spawn tout en ayant un radius confortable autour des meubles : dessiner le contour extérieur du NavigationPolygon plus grand que la pièce visuelle (au moins X + agent_radius si un marker doit être atteignable à la position X).

# -- 7. Resources à créer avant de câbler la scène -- #

- RestaurantData (une par resto, réutilisée par tous ses niveaux) :
  - Restaurant Name
  - Total Levels

- LevelData (une par niveau, ex: level_data_restoA-j2.tres) :
  - Restaurant → le RestaurantData du resto
  - Level Number (1, 2, 3...)
  - Level Menu → une LevelMenu existante (jamais dupliquer les aliments)
  - Possible Customers → types de clients pour ce niveau
  - Active Services → array de GameEnums.ServiceType, valeurs valides : 0 (BREAKFAST), 1 (LUNCH), 2 (DINNER) — RIEN D'AUTRE
  - Tray Max Capacity → taille du plateau pour ce niveau

# -- 8. Câblage du LevelManager (checklist, à refaire pour chaque niveau) -- #

Tous ces champs sont des NodePath relatifs à GameplayCore/LevelManager. En supposant la structure de la section 2 (Entities/HUD/GameplayCore/ZoneDeplacement comme enfants directs du niveau) :

- Level Data                → (assigner le .tres du niveau, PAS un NodePath)
- Tray Places                → ../../HUD/Tray_places
- Customer Spawner           → ../../Entities/CustomerSpawner
- Payment Queue              → ../../Entities/Comptoir/Visuals/PaymentQueueComponent
- Day Cycle                  → ../DayCycleComponent
- Order Flow                 → ../OrderFlowComponent
- Spawn Orchestrator         → ../SpawnOrchestratorComponent
- End Of Service Panel       → ../../HUD/EndOfServicePanel
- Level Intro Screen         → ../../HUD/LevelIntroScreen
- Day Results Screen         → ../../HUD/DayResultsScreen
- Earnings Gauge             → ../../HUD/EarningsGauge
- Day Clock                  → ../../HUD/DayClock
- Navigation Region          → ../../ZoneDeplacement
- Spawn Button                → ../../HUD/SpawnButton

Sur WaitingQueueComponent (sous GameplayCore) :
- Order Flow  → ../OrderFlowComponent
- Exit Marker → ../../Entities/CustomerSpawner/SpawnPoint
- Day Cycle   → ../DayCycleComponent
- Position/Rotation/Scale → À AJUSTER manuellement pour que la file d'attente soit visible/logique dans ce niveau

# -- 9. Réglages qui influencent VRAIMENT la difficulté -- #

- Level Number (LevelData .tres) → seul levier branché à la courbe de difficulté automatique (lerp 40%→80%)
- Tray Max Capacity (LevelData .tres) → plus petit = plus de trajets au comptoir, PAS pris en compte par daily_goal
- Nombre de Active Services (LevelData .tres) → allonge la session, le goal grandit proportionnellement (pas "plus dur en %", juste plus long)

# -- 10. Réglages qui s'auto-équilibrent -- #

- Prix du menu : moyenne recalculée automatiquement
- Types de clients (tip_rate) : idem
- Disposition physique des tables : mesurée automatiquement au démarrage (LevelMetricsHelper)

# -- 11. Réglage volontairement constant -- #

- Expert Threshold Percent reste à 150% sur tous les niveaux (décision consciente)

# -- 12. Pièges rencontrés -- #

- Le level_data du LevelManager n'est PAS hérité automatiquement par une nouvelle scène de niveau basée sur GameplayCore.tscn — il faut le réassigner explicitement, sinon le niveau utilise silencieusement le level_data par défaut de gameplay_core.tscn.
- Dupliquer une scène (Save As) peut casser des exports NodePath si des nœuds ont été renommés/déplacés en cours d'édition — toujours retester après duplication.
